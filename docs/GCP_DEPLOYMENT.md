# GCP Deployment Guide (Illustrative)

> **This document describes templates, not a deployed system.** Everything
> under `deployment/gcp/` is an illustrative, deployable-*shaped* set of
> Terraform files for architecture discussion. **No GCP resources have been
> provisioned, and nothing in this guide has been run against a live GCP
> project as part of this repository's exercise.** Every command below is
> an example of what you *would* run, shown for review purposes -- treat
> project IDs, SKUs/sizes, and IAM bindings as a starting point to adapt,
> not a finished deployment.

## What `deployment/gcp/` provisions

| File | Resource(s) | Role |
|---|---|---|
| `versions.tf` | Terraform/provider version constraints | Pins `hashicorp/google` |
| `variables.tf` | Input variables | Project, region, sizing, and the illustrative tenant-delegation inputs |
| `main.tf` | Cloud Run v2 service, Artifact Registry, Secret Manager, service account, IAM bindings | The control plane itself, plus the illustrative data-plane IAM block |
| `outputs.tf` | Outputs | Service URL, service account email, registry/secret IDs |
| `terraform.tfvars.example` | -- | Example variable values |

All resources are labeled `deployment-status =
"illustrative-template-only"` by default, as a reminder of what they are
if anyone ever did apply them.

### Hypothetical deployment commands

These are examples only -- substitute a real project ID and review the
configuration first:

```bash
cd deployment/gcp

# One-time: initialize providers (downloads the google provider, does not
# touch any GCP project)
terraform init

# Format/syntax check only -- does not touch any GCP project
terraform validate

cp terraform.tfvars.example terraform.tfvars
# edit terraform.tfvars: set project_id to a real project you control

# Show what *would* change, without changing anything
terraform plan -var-file=terraform.tfvars

# Actually deploy (only against a project you control, and only after
# reviewing the configuration)
terraform apply -var-file=terraform.tfvars
```

After a first deployment, the Cloud Run service starts from a small public
placeholder image (`container_image` defaults to
`us-docker.pkg.dev/cloudrun/container/hello`) so the deployment succeeds
before any real image exists. The next step would be building the
`Dockerfile` at the repo root and pushing it to the Artifact Registry
repository provisioned by `main.tf`, e.g.:

```bash
REPO=$(terraform output -raw artifact_registry_repository_url)
docker build -t "$REPO/telemetry-rca-agentic-runtime:latest" ../..
docker push "$REPO/telemetry-rca-agentic-runtime:latest"
gcloud run services update <service-name> --region <region> \
  --image "$REPO/telemetry-rca-agentic-runtime:latest"
```

(again, illustrative -- not run in this exercise.)

## Control plane vs. data plane, on GCP

This configuration provisions the RCA **control plane** only:

- A **Cloud Run v2 service** running the agent runtime, rule engine, jury
  evaluator, and audit log (the code in `agent/`, `rules/`, `evaluator/`,
  `audit/`).
- An **Artifact Registry** repository for that control plane's own image.
- A **Secret Manager** secret for the control plane's own secrets (for
  example an audit-log signing key) -- never tenant data or tenant
  credentials.
- IAM bindings (`roles/monitoring.metricWriter`,
  `roles/cloudtrace.agent`) letting the control plane's own service
  account emit its own operational telemetry to **Cloud Monitoring** and
  **Cloud Trace** in this project. Unlike Azure Log Analytics, there is no
  separate "workspace" resource to create for these -- Cloud
  Monitoring/Trace are platform services enabled per-project via the
  `google_project_service` resources in `main.tf`, and ingestion of real
  OTel data in a production deployment of this repo's ingestion path would
  flow through the same project-level services. (Locally, `otel_mock/`
  stands in for that real ingestion pipeline.)

It deliberately does **not** provision the **data plane**. Each tenant's
own telemetry -- the `logs` / `traces` / `metrics` tables modeled in
`federation/tenant_store.py` and generated by `otel_mock/` for the demo
tenants (`acme`, `globex`, `initech`) -- lives in that tenant's **own** GCP
project, typically as:

- A **BigQuery dataset** queried in place via **BigQuery Omni**
  (cross-cloud / cross-region query-in-place, no data movement), or
- A **BigLake authorized view** over data sitting in the tenant's own GCS
  bucket, or
- A listing shared through **Analytics Hub**.

None of those are created by this configuration, and they should not be:
the whole point of the zero-copy design (see `federation/` and its module
docstrings) is that tenant telemetry never leaves the tenant's own
storage/compute boundary. The control plane only ever holds a *query*, a
*scoped credential*, and the *result rows it was authorized to see* --
never a standing copy of another tenant's data.

## Cross-project IAM: the delegated-access pattern

GCP has no direct analog to Azure Lighthouse's subscription-level
delegation offer/acceptance flow; the equivalent pattern is ordinary,
tenant-granted **cross-project IAM**, scoped as narrowly as the resource
in question allows (ideally a single dataset or authorized view, not an
entire project).

The mechanism, concretely:

1. The **data-owning tenant** (e.g. "acme") decides to share a specific
   BigQuery dataset for federated RCA querying, via one of:
   - **BigQuery Omni**: the control plane queries the dataset in place,
     wherever it physically lives, without the tenant moving or copying
     it into the operator's project.
   - **BigLake authorized views**: the tenant publishes a view with
     row/column-level restrictions already baked in, and only grants
     access to the view -- not the underlying table.
   - **Analytics Hub**: the tenant lists the dataset as an exchange
     listing that the operator's project subscribes to, which creates a
     linked (read-only) dataset in the operator's project without
     copying the underlying data.
2. The tenant grants the control plane's service account a
   **dataset-scoped** IAM role -- `roles/bigquery.dataViewer` at the
   dataset level (via `google_bigquery_dataset_iam_member`, or the
   equivalent `google_bigquery_dataset_access` / dataset `access` block),
   not a project-wide role. This is the least-privilege analog of
   Lighthouse's resource-group-scoped `registrationAssignments`.
3. The control plane authenticates as its own service account (see
   `control_plane_service_account_email` in `outputs.tf`) and runs
   read-only SQL against the tenant's dataset using that grant. No tenant
   credential is ever copied into the operator's project, and no tenant
   data is copied into the operator's project either -- Omni/authorized
   views/Analytics Hub all query or reference the data where it already
   lives.
4. Access can be revoked at any time by removing the IAM binding (or
   un-listing the Analytics Hub exchange), immediately cutting off the
   operator's access, entirely from within the tenant's own project.

`main.tf`'s `google_bigquery_dataset_iam_member.tenant_delegated_read_access`
resource models step 2 in the shape it would actually take. It is a
**no-op by default** (`count = 0`) unless both `tenant_project_id` and
`tenant_dataset_id` are supplied, because applying it for real requires
the tenant's own Terraform/gcloud session and consent -- this module's own
credentials are never sufficient to grant access into someone else's
project. In practice, a tenant would apply their half of this binding from
their own Terraform state, not from this repository's.

This cross-project IAM grant covers authentication/authorization only; it
does not implement row- or column-level scoping by itself (an authorized
view can, but a plain `dataViewer` grant cannot). Finer-grained scoping is
still the job of the federation layer's own access-control model
(`federation/access_control.py`'s `AccessScope`), which is what actually
decides which tenants' tables a given query may touch once the control
plane *can* reach them.

## Explicit caveat

**No real GCP resources were provisioned as part of producing this guide
or the configuration it describes.** The Terraform files under
`deployment/gcp/` are illustrative, deployable-shaped templates meant to
show how the control plane *could* be deployed and how cross-project
delegated access to the data plane *could* be modeled -- they have not
been run through `terraform plan` or `terraform apply` against a live
project, and project IDs/sizing/IAM bindings should be reviewed and
adjusted before any real deployment is attempted.
