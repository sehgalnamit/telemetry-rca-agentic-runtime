# Azure Deployment Guide (Illustrative)

> **This document describes templates, not a deployed system.** Everything
> under `deployment/azure/` is an illustrative, deployable-*shaped* set of
> Bicep templates for architecture discussion. **No Azure resources have
> been provisioned, and nothing in this guide has been run against a live
> Azure subscription as part of this repository's exercise.** Every
> command below is an example of what you *would* run, shown for review
> purposes -- treat names, SKUs, and RBAC scopes as a starting point to
> adapt, not a finished deployment.

## What `deployment/azure/` provisions

| File | Resource(s) | Role |
|---|---|---|
| `main.bicep` | Orchestrator | Wires the modules below together, plus role assignments |
| `modules/monitoring.bicep` | Log Analytics workspace, Application Insights | Control-plane observability |
| `modules/registry.bicep` | Azure Container Registry | Holds the control-plane container image |
| `modules/keyvault.bicep` | Key Vault (RBAC-authorized) | Holds control-plane secrets |
| `modules/containerapps.bicep` | Container Apps managed environment + container app | Runs the control plane itself |
| `lighthouse-delegation.bicep` | `Microsoft.ManagedServices/registrationDefinitions` + `registrationAssignments` | **Standalone**, illustrative Lighthouse delegation -- deployed by a tenant, not by `main.bicep` |
| `main.parameters.json`, `main.bicepparam` | -- | Example parameter files for `main.bicep` |

All resources from `main.bicep` are tagged `deploymentStatus:
illustrative-template-only` by default, as a reminder in the Azure portal
of what they are if anyone ever did deploy them.

### Hypothetical deployment commands

These are examples only -- substitute a real resource group and review the
template first:

```powershell
# One-time: validate the template compiles (does not deploy anything)
az bicep build --file deployment/azure/main.bicep

# What-if: show what *would* change, without changing anything
az deployment group what-if `
  --resource-group <your-resource-group> `
  --template-file deployment/azure/main.bicep `
  --parameters deployment/azure/main.parameters.json

# Actually deploy (only against a subscription/resource group you control,
# and only after reviewing the template)
az deployment group create `
  --resource-group <your-resource-group> `
  --template-file deployment/azure/main.bicep `
  --parameters deployment/azure/main.parameters.json
```

Or with the `.bicepparam` file instead of the classic JSON parameters file:

```powershell
az deployment group create `
  --resource-group <your-resource-group> `
  --parameters deployment/azure/main.bicepparam
```

After a first deployment, the Container App starts from a small public
placeholder image (`containerImage` defaults to
`mcr.microsoft.com/k8se/quickstart:latest`) so the deployment succeeds
before any real image exists. The next step would be building the
`Dockerfile` at the repo root and pushing it to the Container Registry
provisioned by `modules/registry.bicep`, e.g.:

```powershell
az acr build --registry <registry-name> --image telemetry-rca-agentic-runtime:latest .
az containerapp update --name <container-app-name> --resource-group <your-resource-group> `
  --image <registry-login-server>/telemetry-rca-agentic-runtime:latest
```

(again, illustrative -- not run in this exercise.)

## Control plane vs. data plane, on Azure

This template provisions the RCA **control plane** only:

- A **Container Apps environment + container app** running the agent
  runtime, rule engine, jury evaluator, and audit log (the code in
  `agent/`, `rules/`, `evaluator/`, `audit/`).
- An **Azure Container Registry** for that control plane's own image.
- A **Key Vault** for the control plane's own secrets (for example an
  audit-log signing key) -- never tenant data or tenant credentials.
- A **Log Analytics workspace + Application Insights** component, both
  for the control plane's own operational telemetry today, and as the
  landing zone for real OTel ingestion in a production deployment of this
  repo's ingestion path. (Locally, `otel_mock/` stands in for that real
  ingestion pipeline.)

It deliberately does **not** provision the **data plane**. Each tenant's
own telemetry -- the `logs` / `traces` / `metrics` tables modeled in
`federation/tenant_store.py` and generated by `otel_mock/` for the demo
tenants (`acme`, `globex`, `initech`) -- lives in that tenant's **own**
Azure subscription, in one of:

- An **Azure Data Explorer (ADX)** cluster/database, or
- A **Synapse serverless SQL pool** over the tenant's own ADLS Gen2
  storage account, or
- **Microsoft Fabric OneLake**, consumed via OneLake shortcuts.

None of those are created by this template, and they should not be: the
whole point of the zero-copy design (see `federation/` and its module
docstrings) is that tenant telemetry never leaves the tenant's own
storage/compute boundary. The control plane only ever holds a *query*, a
*scoped credential*, and the *result rows it was authorized to see* --
never a standing copy of another tenant's data.

## How Azure Lighthouse enables cross-tenant delegated access

Azure Lighthouse is the mechanism that lets the RCA control plane's
principal(s) run read-only queries against a tenant's ADX/Synapse/Fabric
resources *without* the control plane operator ever holding a subscription
of their own inside that tenant, and without any tenant credential being
copied into the control plane.

The mechanism, concretely:

1. The **data-owning tenant** (e.g. "acme") deploys a
   `Microsoft.ManagedServices/registrationDefinitions` resource in their
   own subscription. This resource names the **managedBy tenant** (the RCA
   operator's Azure AD tenant) and lists one or more `authorizations`:
   pairs of `(principalId, roleDefinitionId)` describing which principal
   in the operator's tenant gets which built-in Azure role.
2. The tenant then deploys a
   `Microsoft.ManagedServices/registrationAssignments` resource, scoped to
   a **specific resource group** (not necessarily the whole subscription)
   -- in this architecture, the resource group holding their ADX
   cluster/Synapse workspace/Fabric capacity. This is the acceptance step:
   it activates the delegation for that scope.
3. Once active, the principal(s) named in step 1 show up as guest
   principals in the tenant's subscription, holding exactly the RBAC roles
   granted -- for example `Reader` and `Monitoring Reader`, as modeled in
   `lighthouse-delegation.bicep`. They can run read-only KQL/SQL queries
   against the delegated resource group's resources using their own Azure
   AD identity from their own tenant; there is no shared secret, no copied
   service principal key, and no data replication step.
4. Everything still happens **inside the data-owning tenant's subscription
   boundary**. The delegation can be revoked at any time by deleting the
   registration assignment, immediately cutting off the operator's access.

`deployment/azure/lighthouse-delegation.bicep` models steps 1-2 in the
shape they would actually take, as a template the **tenant** would deploy
(`targetScope = 'subscription'`, with `managedByTenantId` set to the RCA
operator's tenant ID). It is intentionally **not** referenced from
`main.bicep` -- it has a different deployer, a different subscription
context, and (in a real engagement) would go through the tenant's own
review process before being applied.

Lighthouse grants the underlying **Azure RBAC**; it does not by itself
implement row- or column-level scoping. That finer-grained scoping is
still the job of the federation layer's own access-control model
(`federation/access_control.py`'s `AccessScope`), which is what actually
decides which tenants' tables a given query may touch once the control
plane *can* reach them.

## Explicit caveat

**No real Azure resources were provisioned as part of producing this
guide or the templates it describes.** The Bicep files under
`deployment/azure/` are illustrative, deployable-shaped templates meant to
show how the control plane *could* be deployed and how cross-tenant
delegated access to the data plane *could* be modeled -- they have not
been validated against a live subscription, and names/SKUs/network
settings should be reviewed and adjusted before any real deployment is
attempted.
